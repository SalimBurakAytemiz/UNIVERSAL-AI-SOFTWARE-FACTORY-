# Work OS store (V7 B1, hardened in B2)

One canonical store for user work: projects, missions, tasks. The Control API intake routes are the only writers today.

## Data model
- Project: `projectId (prj_*), orgId, tenantId, customerId?, name, repository?{path|url}, environmentId, createdAt, createdBy`
- Mission: `missionId (msn_*), projectId, tenantId, title, objective, acceptanceCriteria[], riskLevel R0-R4, status, createdAt, createdBy, traceId (trc_*)`. Status follows `core/mission/state-machine.ts`; new missions start `DRAFT`.
- Task: `taskId (tsk_*), missionId, projectId, tenantId, title, status, dependsOn[]`
- IDs are a prefix plus 24 hex chars from `crypto.randomBytes(12)`.
- Every read takes a scope `{tenantId}`; other tenants' entities are never returned.

## Persistence
Data root: `UASCO_DATA_DIR`, default `<repo>/.ai/runtime/workos` (git-ignored runtime area).
- `journal.jsonl`: append-only, one JSON object per line: `{seq, prevHash, hash, type, actor, at, payload}`. `hash = sha256(stableStringify(entry without hash))`; `seq` starts at 1 and `prevHash` of entry 1 is 64 zeros. Types: `PROJECT_CREATED`, `MISSION_CREATED`, `TASK_CREATED`, `MISSION_TRANSITIONED`. Appends are fsynced. The journal is the only authority.
- `snapshot.json`: derived state plus `lastSeq`/`lastHash`, written atomically (`writeJsonAtomic`). It can be deleted and is rebuilt from the journal on load. It may lag the journal (crash between the two writes) but may not be ahead of it or point to a hash that is not in the journal.
- Idempotency: create calls may carry `idempotencyKey` (per tenant and entity kind). The internal key is `JSON.stringify([tenantId, kind, key])`, so tenants cannot collide. Each key stores a payload digest: a repeated key with the same payload returns the existing entity, writes no entry and the API audits `WORKOS_IDEMPOTENT_REPLAY` (HTTP 200); a repeated key with a different payload fails with `WORKOS_IDEMPOTENCY_CONFLICT` (API 409 `IDEMPOTENCY_CONFLICT`).
- Cross-process safety: every journal verify-and-append runs under `journal.lock` (`automation/lib/process-lock.mjs`, same-host dead-PID stale recovery, 10 s wait then `WORKOS_UNAVAILABLE`). Reads compare a journal signature (size, mtime, inode) and re-verify the chain when another process or instance changed it.

## Failure modes
- Broken hash, sequence or `prevHash`, non-JSON line, unterminated last line, illegal replayed transition, or a snapshot ahead of / inconsistent with the journal: the store is marked tampered. Reads and writes throw `WORKOS_JOURNAL_TAMPERED` (API: 503). Nothing is repaired automatically.
- Any other load error (IO error, malformed payload, TypeError while replaying) is atomic: state is only replaced on full success, otherwise reads and writes fail closed with `WORKOS_UNAVAILABLE` (API 503). The next successful load clears the flag.
- `repository.url` containing userinfo (`user:pass@`, `token@`) is rejected (API 400).
- Unknown errors in the Work OS routes return `500 {"error":"INTERNAL_ERROR"}` with no path or stack.
- Before every write the journal is re-read and re-verified, so a second process or an out-of-band edit is detected.
- Invalid mission transition: `WORKOS_INVALID_TRANSITION` (API 409), nothing written. Unknown or other-tenant entity: `WORKOS_NOT_FOUND` (404). Bad input: `WORKOS_INVALID_INPUT` / schema failure (400).
- API write gates, in order: Global Stop active (423 `GLOBAL_STOP_ACTIVE`), action-gateway deny (403 with reason), strict body schema (400). The stop file is only read, never written.

## Worker runs (V7 B3a mission runner)
Runs live in the same journal (no second store). Entry types: `RUN_CREATED`, `RUN_LEASE` (ACQUIRE/RENEW/TAKEOVER), `RUN_TRANSITION`, `RUN_CHECKPOINT`, `RUN_EVIDENCE`. A mission status change caused by a run is embedded in the same entry (`payload.mission = {missionId, from, to, reason}`) so run and mission move atomically; replay still checks it against `core/mission/state-machine.ts`.
- Run: `runId (run_*), missionId, projectId, tenantId, roleId|null, executor{implementer, reviewer}, leaseId, leaseExpiresAt, attempt, status, step, remediationCycle, retryCount, retryAt, reason, baseSha, headSha, workBranch, checkpoints[], evidence[]`.
- Statuses (Master §06) and the allow-listed transition table: `core/workos/run-state.ts`. Illegal replayed transitions mark the journal tampered.
- Fencing: every run write must carry the current, unexpired `leaseId` (`WORKOS_LEASE_FENCED`, API 409). Only an expired lease can be taken over; takeover issues a new `leaseId` and moves the run to `RECOVERING`.
- Engine: `core/workos/runner.ts` (`MissionRunner.tick()`, single-flight, `runner.lock` process lock). Steps: WORKSPACE (`<dataDir>/runs/<runId>/work`, `git clone --no-hardlinks` of `repository.path`, base SHA recorded; url repos -> BLOCKED `REMOTE_REPO_NOT_SUPPORTED_YET`) -> IMPLEMENT -> VERIFY (secret scan of the base..head diff, then the allow-listed argv `testCommand` with `safeChildEnv` and a timeout) -> SECURITY (see "Security stage (V7 B3C)") -> REVIEW (fresh clean clone at the produced commit, reviewer identity must differ, clone must stay unmodified) -> REGRESSION (tests again in a fresh clone) -> REPORT (`report.json`). The run ends `AWAITING_APPROVAL`, the mission `REPORTING`; the runner never merges, pushes or completes a mission.
- Remediation (failed tests, reviewer BLOCKED, failed regression) is bounded (default 2 cycles) then BLOCKED. Transient executor failures retry at most 2 times with backoff, IMPLEMENT only after resetting the workspace to the cycle start commit.
- GLOBAL_STOP is checked before and between steps and polled during child processes: run `CANCELLING -> CANCELLED`, mission `BLOCKED`.
- Executors: `core/workos/executors.ts`. FAKE is test-only (programmatic injection). LOCAL_CLAUDE is off unless `UASCO_WORKOS_EXECUTOR=local-claude`; an implementer identity equal to the reviewer identity is refused.
- API: `POST /v1/missions/:id/runs`, `GET /v1/work-runs?missionId=`, `GET /v1/work-runs/:id`. The in-process tick runs only with `buildServer({runner:{enabled:true}})` or `UASCO_WORKOS_RUNNER=1`.
- Edit-only builder (`EditOnlyImplementer`, `core/workos/builder-output.ts`): LOCAL_CLAUDE runs `scripts/claude-builder-broker.mjs` unchanged under `config/builder-execution-policy.json` (no Bash, so the builder cannot commit). After the broker exits 0 the engine commits on its behalf: the `.git` control files (everything except `objects/` and `index`) must be byte-identical to before the builder ran (else BLOCKED `BUILDER_TOUCHED_GIT_INTERNALS`), the index is rebuilt from the cycle start commit, changed paths are refused when they touch `.git` internals, leave the workspace, are symlinks, embedded repos or gitlinks (`BUILDER_CHANGED_FORBIDDEN_PATH:*`), no change gives BLOCKED `BUILDER_PRODUCED_NO_CHANGE`, and the commit is made with isolated git as `UASCO Builder (CLAUDE_BUILDER) <builder@local.invalid>` on the run branch; its SHA is the run `headSha` used by VERIFY, REVIEW and REGRESSION.
- Secret scan: VERIFY scans in a fresh clone of the produced commit (`<run>/scan-c<cycle>`), never in the implementer workspace, with `git diff --text --no-textconv --no-ext-diff` and an empty `core.attributesFile`, so workspace `.git/config` textconv drivers and `-diff`/binary attributes cannot hide content. Commit messages `base..head` are scanned too (hit file `commit-message:<sha>`). The diff parser tracks hunk line counts, so `+++ `/`--- ` lines inside a hunk are content. The reviewer diff uses the same flags.
- Known limitation (Windows): only `node` in `testCommand` is resolved to `process.execPath`; other allow-listed executables are spawned by name with `shell:false`, so `.cmd` shims (`npm`, `npx`, `pnpm`, `yarn`) cannot be spawned and the run is BLOCKED `TEST_COMMAND_SPAWN_FAILED`. Use `["node", "<script>"]` on Windows.

## Live LOCAL_CLAUDE mission smoke (V7 B3B)
`scripts/workos-live-smoke.mjs` runs ONE real mission end to end with the local Claude Code CLI (provider usage, so it is not part of the vitest suite and never runs in validation).
- Prerequisites: the Claude CLI is logged in, and `node scripts/capture-provider-provenance.mjs` has written `.ai/runtime/PROVIDER_PROVENANCE.json` with `final: PASS` in the control root (the clone you run from). The broker and the reviewer adapter refuse to start otherwise.
- Dry run without any provider: `node scripts/workos-live-smoke.mjs --fake-plumbing` (FAKE executors injected programmatically; evidence only in the temp data dir).
- Live run: `UASCO_LIVE_SMOKE=1 node scripts/workos-live-smoke.mjs [--evidence-out <repo-relative path>]`. Without `UASCO_LIVE_SMOKE=1` it refuses; it also refuses when the control root's `GLOBAL_STOP.json` is active.
- What it does: creates `%TEMP%/uasco-b3b-live-*/sample-repo` (Node project: `src/add.js` stub, `test.js` with `node:assert`, test command `["node","test.js"]`), then through the Control API in process (`app.inject`, no listening socket; temp `runtime` and `data` dirs) creates the project and mission, moves the mission `DRAFT -> PREFLIGHT -> AUTHORIZED` as the Founder, and starts one run with `UASCO_WORKOS_EXECUTOR=local-claude`. The built-in runner ticks every second (max 1 remediation cycle, no transient retries, 60 s test timeout, 15 min per executor call); the script polls `GET /v1/work-runs/:id` until a terminal state or `AWAITING_APPROVAL`. Hard limit 25 minutes: then it activates GLOBAL_STOP in the temp runtime so the runner cancels the run.
- Evidence: a redacted JSON summary (run/mission status timeline from the journal, produced commit and diff, test exit codes before/verify/regression plus an independent re-run in a fresh clone, reviewer verdict and identity, durations, evidence log hashes re-verified) is written to `<data>/live-smoke-evidence.json` and, for live runs, to `audit/checkpoints/V7-PKG-B3B-LIVE-SMOKE-EVIDENCE-2026-10-14.json` by default. Exit code 0 only when the mission is `REPORTING` and the run `AWAITING_APPROVAL`. The runner never merges, pushes or completes the mission.

## Security stage (V7 B3C)
Master V2 section 07 pipeline: QA (VERIFY) -> Security -> independent review. The run step `SECURITY` sits between VERIFY and REVIEW (run status `VERIFYING`; the mission moves `VERIFYING -> REVIEWING` when SECURITY completes). Code: `core/workos/security-tools.ts`, step in `core/workos/runner.ts`.
- Tool contract (599 section 4.3, TOOL_LISTED != INSTALLED != PERMITTED != TESTED): at engine start each of gitleaks, trivy and semgrep is resolved once by a PATH lookup (absolute PATH entries only, `.exe`/`.com` on Windows, no shims) to an absolute path; the version comes from `--version` and the binary sha256 is recorded. Result per tool: `{tool, status INSTALLED|NOT_INSTALLED|ERROR, path, version, sha256}`, exposed as `MissionRunner.securityTools` and written into every SECURITY_REPORT. Before each use the binary hash is re-verified (`TOOL_BINARY_CHANGED` -> fail-closed). Tool paths can only be injected programmatically (`RunnerOptions.security.tools`, also `buildServer({runner:{security}})`), never through the environment.
- Where it runs: never in the implementer workspace. The built-in diff and commit-message secret scan (kept from VERIFY) and trivy run in a fresh checked-out clone (`<run>/security-c<cycle>`); gitleaks runs against a fresh BARE clone (`<run>/security-gl-c<cycle>.git`), so a committed `.gitleaksignore` or `.gitleaks.toml` has nothing to be read from.
- Secrets: `gitleaks git --redact --config <engine toml with useDefault> --gitleaks-ignore-path <empty engine file> --ignore-gitleaks-allow --log-opts "--text --no-textconv --no-ext-diff --diff-merges=first-parent <base>..<head>"`. Only the commit range base..head is scanned; `--diff-merges=first-parent` makes `git log -p` emit a patch for merge commits (without it, content introduced only by a merge commit, such as an evil merge or a conflict resolution, was never scanned); `--text` defeats `-diff`/binary attributes and textconv; the raw JSON report is deleted after parsing (it can carry unredacted commit messages) and only its sha256 is kept. Findings are summarised as `{ruleId, file, line, commit}`, never values.
- Dependencies: `trivy fs --scanners vuln --skip-db-update --skip-java-db-update --offline-scan --skip-check-update --skip-vex-repo-update --skip-version-check --disable-telemetry --config "" --ignorefile ""` on the fresh clone with an explicit `--cache-dir`; the run directory is the only output location. The vulnerability DB is never downloaded: the engine reads `<cache>/db/metadata.json`; a missing or unreadable DB means trivy is not started and the result is `PARTIAL` / `TRIVY_DB_UNAVAILABLE`; a DB older than 7 days (`maxTrivyDbAgeMs`) is used but still `PARTIAL` (`dbState STALE`); a DB error from the run itself is also `PARTIAL`. Trivy missing is `NOT_INSTALLED` (`TOOL_NOT_INSTALLED`).
- SAST: semgrep is only discovered. If it is not installed SAST is recorded as `NOT_AVAILABLE` / `TOOL_NOT_INSTALLED`; if it is installed it is still `NOT_AVAILABLE` / `TOOL_INSTALLED_NOT_INTEGRATED` (no semgrep run exists yet). SBOM is recorded `NOT_AVAILABLE` / `NOT_IMPLEMENTED`. These two standing gaps are always listed in `gaps` and in the founder note but do not downgrade the status.
- Policy: any gitleaks or built-in secret hit -> run `BLOCKED` `SECRET_DETECTED`; trivy HIGH/CRITICAL -> run `BLOCKED` `VULNERABLE_DEPENDENCY` (findings: package, version, CVE id, severity, fixed version, target; MEDIUM/LOW are recorded and not blocking); a scanner crash, bad exit code, unparsable or oversized report, or a changed binary -> `BLOCKED` `SECURITY_TOOL_ERROR` (never a clean result). A timeout or spawn failure is a transient failure: bounded RETRY of the whole SECURITY step. In every BLOCKED case the mission becomes `BLOCKED` and review never starts. Stage status values: `PASSED`, `PARTIAL` (gitleaks or trivy not installed, DB unavailable/stale), `BLOCKED`.
- Process rules: tools run with `safeChildEnv`, `shell:false`, argv arrays, a timeout (default 10 min) and the run's GLOBAL_STOP/lease poll (the child tree is killed and the run is CANCELLED). Output is bounded (captured stdout/stderr 4 MB, report files 32 MB). The step is stateless, so crash-resume and RETRY re-entry rebuild the clones and rescan; the checkpoint is written after SECURITY.
- Evidence: `SECURITY_GITLEAKS` and `SECURITY_TRIVY` (redacted process logs + sha256) and `SECURITY_REPORT` (`logPath` = `security/security-report-c<cycle>-a<attempt>.json` with sha256, plus `evidence.security` = the redacted `SecurityStageSummary`: tools, secrets, sca, sast, sbom, gaps, `founderNote`; at most 50 vulnerabilities inline, the full list is in the report file). `GET /v1/work-runs/:id` therefore shows the stage summary with no route change.
- Founder visibility: `report.json` gets a `security` section with the `founderNotice`. When the stage is `PARTIAL` the run ends `AWAITING_APPROVAL` with reason `DELIVERY_DECISION_PENDING_FOUNDER; SECURITY_COVERAGE_PARTIAL` (a PASSED stage keeps `DELIVERY_DECISION_PENDING_FOUNDER`). There is no inbox module in this base; the report, the run reason and the evidence are the Founder-facing surface. REPORT refuses to complete without a non-BLOCKED SECURITY_REPORT for the head commit (`SECURITY_EVIDENCE_MISSING`).
- Tests: `tests/v7-b3c-security-stage.test.ts` uses a FAKE scanner (`core/workos/fake-security-tool.mjs`, injected through `fakeSecurity()`), so it does not depend on host tools; one case runs the REAL gitleaks when it is installed and reports an explicit SKIPPED otherwise.
