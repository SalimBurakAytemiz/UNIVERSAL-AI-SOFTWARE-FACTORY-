# LANE-C map (agents / Work OS / tools)

- Definition vs running agent: `core/agents/role-execution.ts` — `RoleExecutionProfile` (data on a role definition) vs `RunningAgent` (needs EXECUTABLE resolution + runId; tool gate; trace envelope).
- Bindings: `core/agents/first-delivery-bindings.ts` — pre-dev primaries business analyst UASCO-0022, requirements engineer 0023, UX designer 0031, then planner 0019, architect 0043, developer 0085, tester 0313, security reviewer 0252, delivery 0232. All other roles: `NOT_EXECUTABLE:ROLE_HAS_NO_BINDING`.
- Certification: never granted; `EVALUATED_PASS` only if all catalog evaluationSpecs PASSED with evidence (today 0/3594).
- Tools: only `config/builder-execution-policy.json` allowedTools; reviewer-route read-only; delivery uses no model tools (ProjectStudio).
- Wired: `crewDevExecutors` (core/workos/crew/dev-review.ts) is fail-closed via `assertRoleExecutes` (developer / security-reviewer). Team summary reports per-role executability (read-only). Runner IMPLEMENT step blocks a run whose roleId has no executable developer binding (roleId null = unchanged). Next: widen guild by guild.
- Routing/recovery: `core/agents/agent-routing.ts` — read-only provider route readiness (no login => NOT_READY, never personal profile) and agent checkpoint/restore (fail-closed on corruption, missing/changed/incomplete binding).
- Runner IMPLEMENT gate accepts implementer-route roles (developer 0085, tester 0313) via `assertImplementerRole`.
- Run evidence: role-assigned runs write `AGENT_TRACE` for IMPLEMENT (bound implementer) and REVIEW (bound security-reviewer, verdict in note). - Tests: tests/v7-b3a-runner.test.ts (LANE-C role gate + AGENT_TRACE); `tests/v7-core-predev-team-composer.test.ts` ("LANE-C role execution resolver").
- Runner claim cap (C5a): `RunnerOptions.maxConcurrentRuns` (default 1, valid 1..16, else `RUNNER_MAX_CONCURRENT_RUNS_INVALID`). A tick takes a lease only while fewer than the cap runs are owned (new claims and stale-lease takeovers); the rest stay QUEUED and are reported in `TickReport.deferred`. Fixes: with several queued runs the old tick leased all of them up front and drove them serially, so a queued run's lease expired unrenewed while an earlier run executed and it was fenced and later "recovered" (spending recovery budget). Owned runs are driven together (`Promise.all`); cap 1 is the old serial behaviour. Not done: workspace cleanup after terminal states (ProjectStudio reads run commits from `runs/<id>/work/.git/objects`, so deleting the workspace needs a commit-retention design first).
- Task limits (C3a): the runner applies a bound role's `TaskLimits` to its run via `effectiveLimits` (only ever tightens the run defaults): `maxCycles` -> at most `maxCycles-1` remediations (`*_TASK_LIMIT_MAX_CYCLES_EXHAUSTED`), `timeoutMs` -> implementer timeout, `maxFilesWritten` -> files changed vs the run base after IMPLEMENT (`TASK_LIMIT_FILES_EXCEEDED:<n>><max>`, BLOCKED before VERIFY; unreadable count -> `TASK_LIMIT_FILES_UNVERIFIABLE`). Role-less runs are unchanged. Developer/tester `timeoutMs` = 60 min (the runner's existing default). REVIEW stage (security-reviewer `lim(1, 0, 60 min)`): `timeoutMs` -> reviewer timeout via `effectiveLimits` (min of run default and role limit); `maxFilesWritten` 0 is the existing untouched-clone gate (`REVIEWER_MUTATED_CLONE`) plus `profileDefect`; `maxCycles` 1 = one review pass per REVIEW step (the remediation loop is bounded by the implementer role's `maxCycles`). Changing a binding limit requires `node scripts/build-role-execution-profiles.mjs`.
- Profiles (C2): `scripts/build-role-execution-profiles.mjs` (+ `--check`, byte-identical rebuild) derives `registries/role-execution-profiles.json` for all 599 roles from in-repo sources only via `core/agents/role-profile-derivation.ts`. Every field is PROPOSED_DERIVED with provenance; empty fields carry a gap id; write route only with SEMANTIC_VERIFIED technical legacy evidence, otherwise read-only; never production/network/secret/payment/deployment grants; reviewer != self. It is a proposal, NOT a binding: nothing becomes executable/tested/certified from it.

- Run workspace archive (C5b, default OFF): `core/workos/run-archive.ts` `RunWorkspaceArchiver.sweep()` archives a terminal managed run's RECORDED commit set (headSha + evidence commitSha's) under `refs/uasco/run-commits/<runId>/<sha>` (+ `refs/uasco/runs/<runId>` for the head) via the existing ProjectStudio import, re-verifies each without alternates, writes `runs/<id>/workspace-archive.json`, then removes derived clones and `runs/<id>/work` after the retention period. - Role readiness audit (C-RDY-1): `core/agents/readiness-audit.ts` `computeRoleReadiness` is the AUTHORITATIVE readiness measurement: 8 tri-state layers (DEFINED, PROFILED, KNOWLEDGE_READY, TOOL_READY, EXECUTABLE, EVALUATED, INTERNALLY_CERTIFIED, RUNNING; TRUE/FALSE/UNKNOWN with closed reason codes and real denominators) per canonical role, rolled up for 51 guilds and 10 clusters, plus `EXECUTABLE.stageWired` reported SEPARATELY (never merged, never defaulted: UNKNOWN without `reachableStages`). A JSON status is never evidence, PROPOSED_DERIVED data is never PROFILED, no empty list is TRUE, RUNNING is UNKNOWN (not 0) unless the journal is explicitly PRESENT with a runs array (`RunsObservation` in `core/agents/role-lifecycle.ts`; undefined or unknown values are ABSENT), a group with denominator 0 is never `measured` (coordinator-approved amendment to the dispatch after the #260 review: `measured = denominator > 0 && UNKNOWN === 0`), duplicate guild / binding / proposed-profile keys are an input error (`READINESS_INPUT_INVALID:<code>:<key>`; a duplicate ROLE id stays a DEFINED finding), a non-default `promotedTechnologyStatuses` is disclosed in `inputs` and labels the result NON_AUTHORITATIVE_PROMOTED_STATUS_OVERRIDE, and `PROMOTED_TECHNOLOGY_STATUSES` is the empty set until FD-1/FD-9 decide. EXECUTABLE/EVALUATED/INTERNALLY_CERTIFIED call `roleLifecycle()` (no rule copy); `computeRoleStatusSummary` is `@deprecated` (DEPRECATED_LEGACY_PROJECTION, byte-compatible) and `reconcileLegacyStatusSummary` compares it to the audit in total and per guild. `loadReadinessInputFromRepo` reads six registry groups read-only and throws `READINESS_INPUT_UNAVAILABLE:<path>` instead of substituting empty data; empty `roles` / `guilds` / `clusters` / `skills` arrays are rejected the same way (amendment above). - Adapter reality map (C-RDY-2a): `core/capabilities/adapter-reality.ts` maps adapter ids (registry ids, including `omniroute` as a DISCOVERY_ONLY script record (`runs: false`: one policy-gated GET `<gateway>/models` run by hand; no production code routes a model call through OmniRoute), real-but-unregistered tools git/npm/node/claude-cli, and the 10 distinct FIRST_DELIVERY_BINDINGS adapter ids) to the real module + named export (+ class member) + declared production callers, and verifies each by READING source (no module is executed, no binary installed or run); a declared caller must be a production source path (under apps/core/scripts/automation, not a test, docs, node_modules or an outside/absolute path). A small scanner (`codeViews`) blanks comments and string/template/regex bodies first, so a mention in a comment or an error message never counts: `verifyRecord` gives codePath PRESENT only when the record's hand-set `runs` claim is true, the export (or, for a script, its literal name) is declared in CODE, a class member is declared in its own class, and at least one declared caller really references the symbol in code (a quoted import specifier or script path is matched as a real string literal, never inside another string); `entrypoint` exempts only a SCRIPT_LITERAL script from the caller requirement. PRESENT therefore means "declared, wired in code, claimed to run", it is NOT proof that the tool runs (`runs` is a claim; execution evidence is the probe and `ciEvidence`). Probes default to NOT_OBSERVED and only a caller-supplied observation changes them, so C-RDY-1 `TOOL_READY` is UNKNOWN 9 until every binding adapter is observed READY. `reconcileAdapterReality` reports UNDER_REPORTED (6 code-backed registry ids that the registry still calls NOT_IMPLEMENTED: ajv, ajv-formats, github, gitleaks, playwright, trivy), OVER_REPORTED (0), UNREGISTERED_REAL (git, npm, node, claude-cli: the recorded unregistered tools, not every host command), DEAD_CODE (`core/capabilities/resolver.ts` has no production importer) and ADAPTER_UNRESOLVED; it edits no registry (Lane S / Z1 decide). `ciEvidence` classes are honest (REAL and REAL_WHEN_CONFIGURED only for a token that a workflow contains, comments excluded; npm and node REAL (ci.yml runs ensure-dependencies and run-validation), github REAL_WHEN_CONFIGURED (the independent-review workflow runs the real REST client only behind its trigger/environment/non-draft gate), gitleaks FAKE_BINARY_ONLY, trivy FAKE_ONLY, playwright HARNESS_NOT_CI, semgrep DISCOVERY_ONLY); the set of tools any workflow mentions is pinned explicitly, so a PR that adds one (gitleaks/trivy in CI, #251) fails loudly until its class is decided. A completeness census (`censusProduction` / `censusProblems`) fails when a registry id or a spawned command appears in production code (comments excluded, strings included) with neither a record nor a justified `CENSUS_EXCLUSIONS` entry (docker/appium/adb/helm/ffmpeg: presence names checked with which/where in doctor and run with `--version` in preflight; cargo/gradle/cypress: test-command tables; spark: UI keys; host utilities), and for stale exclusions; commands resolved through variables (`run("gh", ...)` wrappers) are not seen by it, and the scanned sources are ts/mts/mjs/cjs/js only: PowerShell (`.ps1`) scripts, such as `scripts/ensure-omniroute.ps1` that starts the OmniRoute launcher, are a known blind spot (pinned by a test; omniroute is the only registry id this hides, and it is mapped explicitly). `resolveCapabilityFromReality` in `core/capabilities/resolver.ts` takes tool health from the map (code PRESENT + probe READY), never from the registry `implementation` field or a caller boolean.
