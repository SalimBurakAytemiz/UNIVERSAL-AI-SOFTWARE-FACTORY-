# Cloud merge gate (CP-MERGE-GATE)

Authority: Founder directive 2026-10-20 "CLOUD PRODUCTION RECOVERY", section 4 (code-enforced merge gate inside the existing architecture, no protected-file or trust-root change). The gate is a decision module. It never calls GitHub and never merges; the coordinator gathers the evidence and performs the merge.

```
node docs/planning/merge-gate.mjs --evidence <file.json> [--mode process|strict] [--policy <file.json>]
node docs/planning/merge-gate.mjs --post-merge <file.json>
```

It prints exactly one JSON line: `{decision, expectedHeadSha, expectedBaseSha, reasons[], identityIndependence, trust, mode, riskTier, riskClasses[]}`. The exit codes are 0 for `MERGE`, 2 for `BLOCK` and 3 for `INTERNAL_ERROR`, which is also fail-closed. The proof is `node docs/planning/merge-gate.proof.mjs`; CI runs it from `tests/review-governance.test.ts` (through `tests/support/merge-risk.cases.ts`), together with the classifier's and the PR controller's mutation proofs (`docs/planning/merge-risk.proof.mjs`, `docs/planning/pr-controller.proof.mjs`) and a step-by-step agreement scenario between the controller and this gate (`tests/support/pr-controller.cases.ts`).

`riskTier` is `ROUTINE`, `PREAUTHORIZED` or `FOUNDER`, computed per file by `docs/planning/merge-risk.mjs` (COORD-TRANSITION-AUTONOMY, see `docs/authority-requests/COORD-TRANSITION-AUTONOMY.md`). `riskClasses` holds its fixed class codes. When the paths could not be classified, the tier is `FOUNDER` with `RISK_NOT_EVALUATED`.

## Inputs
- **Evidence** (gathered by the coordinator with GitHub tools):
  - `pr {number,state,draft,merged,changed_files,head:{sha,ref},base:{ref,sha},user:{login}}`;
  - `currentBaseSha`, read just before merging;
  - `checkRuns [{name,status,conclusion,head_sha,app_slug,completed_at,workflowPath,workflowRunEvent}]`. `workflowPath` is the check suite's workflow run `path` (for example `.github/workflows/ci.yml`), and `workflowRunEvent` is that run's `event`;
  - `reviews [{id,user:{login},state,commit_id,body,submitted_at}]`;
  - `diffFiles [{filename, previous_filename?, status}]`, in the GitHub PR files API shape. `status` must be one of `added`, `modified`, `removed`, `renamed`, `copied`, `changed` or `unchanged`. `renamed` and `copied` must carry `previous_filename`. The old `ownDiffFiles` field is no longer accepted;
  - `protectedPaths {exactPaths,protectedPrefixes}`, the contents of `config/protected-paths.json`;
  - Optional: `fileContents {"<filename>": {base, head}}`, the text of a changed file read at the exact base and head SHAs. Only the four pre-authorized class targets use it (`apps/control-api/src/server.ts`, `apps/desktop/main.mjs`, `config/validation.json`, `config/trust-root-manifest.json`). It is keyed by the exact `filename`; a missing or non-string side counts as missing.
  - Optional: `headFiles []`, paths known to exist at the head (for a test registered in `config/validation.json` that the PR does not itself add). The review workflow's `collectEvidence` fills it: for each `tests/*.test.ts` file that the head's `config/validation.json` registers and the base's does not, it asks the contents API at the exact head SHA and lists the file only when GitHub returns a file at exactly that path (at most 20 lookups; an error, a missing file or more candidates leave it out, which keeps the registration FOUNDER).
  - `rules []`, from `GET /repos/{o}/{r}/rules/branches/{base}`.
  - Optional: `implementerSessions []`. A verdict whose `reviewer-session` is in this list is rejected.
  - Any other field, such as `issueComments`, is ignored.
- **Policy** (`--policy`, optional): `{trustedReviewerLogins: [], expectedBaseRef: "v7/integration"}`. The `--mode` flag sets the mode.

**No echo.** Every output string is either a fixed code from this file or a SHA that passed validation. Review bodies, logins, titles, refs, comments, argv values and exception messages never reach stdout or stderr. The proof scans every output for planted markers to check this.

## The binding line the reviewer must post
The reviewer posts it in a PR **review** body (state `COMMENTED` or `APPROVED`), never in an issue comment. It is one line, exactly:

```
VERDICT-BINDING: verdict=CLEAN head=<pr head sha> base=<current base sha> reviewer-session=<id>
```

- `verdict` is `[A-Z_]+`. Only `CLEAN` passes, and any other value blocks the merge if it is at the same time or later.
- `reviewer-session` is `[A-Za-z0-9._:-]{1,128}`.
- A body with more than one `VERDICT-BINDING` line is `AMBIGUOUS`.
- The line must start at column 0 with exactly `VERDICT-BINDING: `. Any other line that mentions `verdict-binding` (in any case, indented, or with trailing text) is `MALFORMED`.
- Invisible characters are every character in `\p{Cf}` (format controls) or `\p{Default_Ignorable_Code_Point}`. This set includes the earlier hand list and U+061C.
  - Any line that contains one of these and mentions `verdict-binding` once they are removed is `MALFORMED`. This holds wherever the line is, including inside a code fence or a quote.
  - Invisible characters are never removed before the fence and quote checks.
- Quoted lines (starting with `>` or `&gt;`) and lines inside code fences never count as bindings.
- A fence opens with a run of 3 or more `` ` `` or `~`. It closes only with a run of the same character that is at least as long and has nothing after it, so `~~~` never closes a `` ``` `` fence.
- Free text and JSON elsewhere in the body are ignored.
- A verdict on an older commit is void.
- `UASCO-LOOP-RECORD ... result CLEAN` issue comments never count.

**Whose reviews count.**
- In process mode, a review counts if it comes from the PR author's account or from a login in `trustedReviewerLogins`.
- In strict mode, only trusted logins other than the PR author count.
- Binding lines in reviews from anyone else are ignored, so an outsider cannot pass the gate.
- The one exception is `CHANGES_REQUESTED`: it blocks from any author, and the cure is dismissing the review.

## Modes and the trust statement
- **Identity.** `identityIndependence` is `DISTINCT_ACCOUNT` only when the verdict author is not the PR author and is in `trustedReviewerLogins`. Otherwise it is `SAME_ACCOUNT`.
- **`process` (default).** `SAME_ACCOUNT` is allowed, and the output says `trust: "PROCESS_ONLY_SAME_ACCOUNT"`.
  - This is a process check only. It proves that a well-formed binding exists for this exact head and base, on green CI, under the required ruleset.
  - It does **not** prove that an independent reviewer wrote it. The builder session runs under the same GitHub account and could post the same line.
  - **No forgery resistance is claimed for same-account verdicts.**
- **`strict`.** `SAME_ACCOUNT` gives BLOCK `REVIEWER_NOT_INDEPENDENT_IDENTITY`. On success the output says `trust: "DISTINCT_TRUSTED_ACCOUNT"`.
  - Even then, the gate only proves that a different GitHub identity posted the line. It does not prove that the reviewer was a fresh, isolated process.
- **`trust`** is `NONE` on any outcome other than MERGE.

### OWNER_ACTION (needed before strict mode can pass)
1. Create a second GitHub identity for the reviewer, either a separate account or a GitHub App, whose credentials the builder sessions do not hold. Give it review permission on the repo.
2. Add `required_approving_review_count: 1` to the `pull_request` rule of the `v7/integration` ruleset, and have the reviewer identity submit the binding line in an `APPROVED` review.
3. Run the gate with `--mode strict --policy <file>`, where the policy file has `{"trustedReviewerLogins":["<reviewer login>"]}`.

Until this is done, only process mode can pass, and it carries `PROCESS_ONLY_SAME_ACCOUNT`.

## How the coordinator uses it
1. **Gather the evidence** with GitHub tools:
   - the PR (`pull_request_read`);
   - the check runs for the head SHA, with `app.slug` mapped to `app_slug`;
   - the PR reviews (not issue comments);
   - the PR file list, as `diffFiles` (`filename`, `previous_filename`, `status`);
   - for each modified pre-authorized target in that list, its text at the base SHA and at the head SHA, as `fileContents` (contents API `?ref=<sha>`; leave a side out when it cannot be read: missing means FOUNDER);
  - for each check run, its check suite's workflow run, which gives `path` as `workflowPath` and `event` as `workflowRunEvent`;
   - `config/protected-paths.json` from the base;
   - the branch rules for `v7/integration`.

   Read `currentBaseSha` (the base branch head) last, just before step 2.
2. **Run the gate:** `node docs/planning/merge-gate.mjs --evidence ev.json [--mode strict --policy pol.json]`.
3. **Merge only if the exit code is 0 and `decision == "MERGE"`.** Call the merge API with `merge_method: "merge"` and `sha: expectedHeadSha`, so GitHub refuses the merge if the head moved. Any other result: do nothing, and report the reason codes. `riskTier` tells who may act: `ROUTINE` and `PREAUTHORIZED` need no Founder (still CI and the independent verdict); `FOUNDER` is never merged by the coordinator, and the coordinator never arms auto-merge on any tier: the Founder merges a FOUNDER-tier PR personally or arms auto-merge on its final head personally.
   - **One merge rule (gate and controller).** The coordinator follows `docs/planning/pr-controller.mjs` `nextActions(state)` per PR. Its `MERGE_HEAD` says that this gate's conditions hold for the head and the base tip, and the coordinator executes it as steps 1 to 4 here: gather the evidence, run the gate, and call the merge API with `sha` = the head SHA only on `MERGE` for the same head and base. The gate is therefore a precondition of every coordinator merge. A verdict from the reviewer App is a check run, not a PR review, so it is the one row (d) this gate cannot see: for an App verdict, the gate's decision counts as `MERGE` when its only reasons are `VERDICT_*` codes and the App check concluded success on this head with its decision bound to this base (a `REVIEW_CHANGES_REQUESTED` still blocks). This is the substitution the App's own `decide` step makes when it runs this gate (it also drops `BASE_DRIFT`, which the controller and this gate keep: base rule below). The conditions are thus the same for both kinds of verdict. `MERGE_HEAD` requires CI PASS bound to the head, a trusted independent PASS (the reviewer App, or a process review recorded as an explicitly independent session) bound to this head and base, no FAIL or unreadable verdict record on the head, no conflict, a tier that is not FOUNDER and no prior negative verdict, the tier and the prior record both computed for this head (`riskTierHeadSha`, `priorNegativeHeadSha`). FOUNDER tier and prior negative always end at `FOUNDER_REQUIRED`: the controller has no input for a Founder approval, and the Founder merges or arms personally. Conflicts, CI failures and review findings go back to the PR's own lane on the same PR.
   - **Base rule.** A PR merges only when `pr.base.sha` (the base its CI merge ref was built from) equals the base tip read last, and the verdict is bound to that same tip: rows b (`BASE_DRIFT`) and d (`VERDICT_BASE_MISMATCH`), and in the controller `prBaseSha == baseSha == verdict.baseSha`. `pr.base.sha` moves only on a head push, so after any merge into the base every other open PR drifts. The controller updates a drifted PR (`UPDATE_BRANCH`, `BASE_MOVED`) only when it is otherwise ready: CI green on its head, no FAIL or unreadable verdict, a tier the coordinator may merge. The update makes a new head; CI runs on the current base, and the verdict is requested again (`REVERIFY`). A PR still in progress (CI failing or pending, a conflict, a negative verdict) is not touched by a base move: its own next step comes first, and its lane's next push refreshes `pr.base.sha` anyway. A FOUNDER-tier or prior-negative PR is never updated or re-verified because of a base move; the Founder chooses when. When `pr.base.sha` already equals the tip but the verdict is bound to another base, the controller re-verifies (`REVERIFY`, `VERIFICATION_STALE_BASE`). There is no file-name exception: a name intersection is not a dependency graph, and this gate has no such exception. Optional strict up-to-date mode in the ruleset would make GitHub enforce the same rule for every merge, an armed auto-merge included.
   - **GitHub auto-merge is not head-bound.** The ruleset enforces only the two `validate` checks, and an armed auto-merge survives pushes by the shared account: on #218 auto-merge was enabled on head `a2ed5c11`, a push of `16f47821` followed, no disarm event was recorded, and GitHub merged `16f47821` on the `validate` checks although the UASCO Independent Review check on it was failure (#212, #219, #222, #223: the same sequence). The coordinator therefore never arms auto-merge and merges itself with `MERGE_HEAD`. On every run the controller disarms an armed auto-merge (`DISABLE_AUTO_MERGE`) unless the caller proves it was armed on the current head (`autoMergeArmedHead`), and it always disarms first when the plan pushes to the PR (`FIX_CI`, `RESOLVE_CONFLICT`, `REMEDIATE_REVIEW`, `UPDATE_BRANCH`; reason `AUTO_MERGE_BEFORE_PUSH`), because the push makes a new head that the arm would merge on the `validate` checks alone. Without a push, an arm on the current head is the Founder's decision and is kept, also next to a reviewer auth failure. Between a push to an armed PR and the controller's next run, GitHub can still merge the new head on the `validate` checks alone; requiring the App check in the ruleset (COORD-TRANSITION-AUTONOMY, "The Founder's free options") closes that window.
   - **Never on the coordinator's or a lane's own authority:** approving a `uasco-founder-authority` deployment, arming auto-merge, or changing rulesets, environments, variables or secrets. All actors use the Founder's account, so GitHub cannot tell these actions apart from the Founder's.
4. **Verify after the merge:**
   - Read the merge commit and the new base head.
   - Run `node docs/planning/merge-gate.mjs --post-merge pm.json` with `{mergeCommitSha, mergeCommitParents, newBaseHead, expectedBaseSha, expectedHeadSha}`.
   - It requires `parents == [expectedBaseSha, expectedHeadSha]` and `newBaseHead == mergeCommitSha`.
   - **Auto-merge chains:** when GitHub merged the PR after other merges, the first parent is a later base commit and the base may already have moved on. Prove it with git and pass `baseIsAncestor: true` (`git merge-base --is-ancestor <expectedBaseSha> <parents[0]>`) and, when the base moved past the merge, `mergeOnFirstParent: true` (the merge commit is in `git rev-list --first-parent <newBaseHead>`). The second parent must still be exactly `expectedHeadSha`. The result then carries `basis: "ANCESTRY_PROVEN"` instead of `"EXACT"`.
   - `MISMATCH` (exit 2) means the merge was not the evaluated one. Stop and escalate; do not merge anything else.

## Limitations
- The gate trusts the evidence file as gathered. A coordinator that fabricates the evidence defeats it. The ruleset's own `required_status_checks` and `pull_request` rules are the server-side backstop.
- There is a time-of-check to time-of-use window between step 2 and step 3. The `sha` parameter covers a head move, but not a base move; a base move after the gate runs is caught only afterwards, by `verifyPostMerge`.
- The controller's state is built by the coordinator from the same GitHub reads (the mapping is in `docs/authority-requests/COORD-TRANSITION-AUTONOMY.md`, "Controller inputs"). Like the evidence file, a fabricated state defeats it.
