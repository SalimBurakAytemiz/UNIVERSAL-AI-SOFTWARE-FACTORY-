## 3. Product orchestration - how the single pipeline really works [V]

1. Founder fills the intake form > `submitIntake` creates project + mission (DRAFT) idempotently (`intake.ts:89-127`).
2. Optional pre-dev chain (analysis > requirements > plan > architecture > UX spec): `POST /v1/missions/:id/analysis/step` builds `AnalysisFlow` with `getExecutors().pair.preDevBuilder()` - only the LOCAL_CLAUDE pair offers it (`executors.ts:49-50,344`). With FAKE or no executor the step is BLOCKED honestly (E2E asserts "analysis shows a draft/complete result while the executor is FAKE" must fail, `desktop-journey.e2e.mjs:249-253`). One produce lock per process (`produce-lock.ts`).
3. `POST /v1/missions/:id/runs` refuses R3/R4 (`riskAdmitted`), requires executors configured and `assertIndependentExecutors`, creates the run with `roleId = DEFAULT_RUN_ROLE_ID` (developer, `server.ts:82,315-324`).
4. Runner claims (CREATED > QUEUED > lease), drives the 7 steps, ends `AWAITING_APPROVAL`; it never merges, pushes or completes (`README.md` workos). Founder transitions REPORTING > COMPLETE manually; delivery acceptance is `SOURCE_DELIVERY_ACCEPTED`, always `productVerification: NOT_VERIFIED`.
5. Any provider quota/rate-limit text from the CLI is classified (`executorLimit`, `runner.ts:91-103`) and ends the run `BLOCKED/PROVIDER_QUOTA`; disk-full is a separate class.
